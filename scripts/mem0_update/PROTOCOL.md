# Mem0 갱신 결정 대체 실험 v1

## 범위

질문은 지속적인 대화 상태를 가진 작은 모델이 Mem0의 LLM 갱신 결정자를 대체할 수 있는지다. 기존 논문 원고는 수정하지 않는다. 별도 검색기, 재정렬기, 근거 주석 생성은 사용하지 않는다. Qwen 또는 다른 답변 LLM의 LoRA 학습도 하지 않는다.

Mem0 0.1.118 (`ed5a1e9fc68fcd7671a70c33a540d24573755449`)의 `_add_to_vector_store`에서 갱신 LLM 호출 하나만 가로챈다. AST 변환은 정확히 한 호출이 일치해야 작동한다. 나머지 사실 추출, 사실별 top-5 기존 기억 검색, UUID 매핑, Qdrant 저장·수정·삭제, 질문 시 검색은 upstream 메서드를 실행한다. 인스턴스 초기화는 동결된 인코더 공유와 대화별 독립 저장소를 위해 별도로 주입한다. 메모리 그래프는 사용하지 않는다.

## 비교 조건과 원본 Mem0와의 차이

주 비교는 LLM 결정자, 상태 없는 작은 모델, FactoredSlot 상태추적기의 세 조건이다. 추출기·교사·문장 생성기·답변기는 `gpt-oss-120b` (AkashML bf16, reasoning low), 채점기는 공식 스크립트의 `gpt-4o-2024-08-06`을 사용한다. 프로젝트 API의 OpenRouter 모델 경로로 호출하며 실제 응답 모델 ID를 기록한다.

원본 Mem0는 연산과 문장을 한 응답에서 동시에 생성한다. **원래 생성 문장을 저장하는 `llm_native` 기준군을 전체 500문항에서 먼저 평가한다.** 문장 생성의 차이를 통제하기 위해 같은 LLM 결정자에 공통 문장 생성기를 붙인 `llm` 경로도 평가한다. 결정자는 여전히 세 종류이며, LLM의 두 생성 경로를 모두 남겨 기준군을 유리하거나 불리하게 바꾸는 일을 방지한다. 공통 생성기를 붙인 기준군을 아무 수정 없는 native Mem0라고 표기하지 않는다. LLM 응답의 원래 문장도 보존한다. 공통 생성기는 결정된 연산·대상을 바꾸지 못하며, 개수·인덱스·빈 문장을 검사해 최대 3회 요청 후 실패한다. 추가 생성 호출과 재시도 비용을 숨기지 않는다.

존재하지 않는 대상 ID 등 원본 Mem0에서 실행되지 않는 교사 연산은 `skipped_teacher_actions`로 보존하고 감독 라벨에서는 제외한다. 실제 저장 효과와 학습 라벨이 일치해야 한다. 실행 중 예상하지 못한 upstream 오류는 실험 실패로 드러낸다. 성공한 기록만 조용히 채점하는 방식으로 실패를 감추지 않는다.

## 학습

평가 데이터를 프롬프트에 넣지 않고 가상 사용자별 16개 세션을 생성한다. 생성 응답이 16개보다 길면 내용이나 점수와 무관하게 시간 순서의 첫 16개를 사용하고 원래 개수를 기록한다. 짧은 응답은 재요청한다. 학습 256명과 검증 32명은 사용자 단위로 분리된다. LongMemEval과 정규화한 긴 발화의 동일 내용 여부를 검사한다. 이는 독립 생성 출처 및 정확 일치 검사이며 의미적 중복까지 완전히 배제했다는 주장은 하지 않는다. 별도의 실제 대화 코퍼스가 아닌 **합성 학습 데이터**라는 한계를 결과에 명시한다.

입력은 새 사실, 검색된 기존 기억, 상황추적기에만 제공되는 현재까지의 대화다. 이전의 FactoredSlot 재귀식과 학습형 슬롯별 입력 경로를 재사용한다. 대화마다 상태를 초기화하고 같은 사용자의 세션 간 상태는 유지한다. 긴 발화는 동결 인코더의 입력 길이에 맞춰 순서대로 나눠 모두 관찰한다. 세션은 시간 순서로 주어진 후 한 번 갱신한다. 질문·정답·`has_answer`·근거 세션 ID는 상태 갱신에 넣지 않는다.

여러 연산을 표현하기 위해 두 모델은 같은 작은 autoregressive decision head를 쓴다. 연산 헤드는 ADD/UPDATE/DELETE/NONE, 대상 헤드는 검색된 기억의 가변 길이 목록을 선택한다. ADD에는 기존 기억 대상이 없다. NONE/null은 연산열 종료를 표시한다. 이 연산열 내부의 decoder 상태와 대화 세션 간 유지되는 FactoredSlot 상태는 서로 다르다. 상태 없는 조건은 대화 이력을 전혀 보지 못한다. 두 모델의 학습 가능한 파라미터 수는 1% 이내로 맞춘다.

손실은 연산 cross-entropy와 대상 cross-entropy의 합이다. 다음 문장 예측, 변화 확률 임계값, 축별 앵커 손실은 사용하지 않는다. 현재 구현은 임의 초기화한 다섯 슬롯을 학습하므로 각 슬롯이 인물·공간·시간·인과·의도로 의미적으로 정렬되었다고 주장할 수 없다. 기존 앵커 체크포인트의 추가 초기화 효과는 이 v1 실험에 포함하지 않는다.

첫 실행은 사용자 요청에 따라 seed 0 하나, 최대 15 epoch, 검증 손실 patience 3으로 checkpoint를 선택한다. 학습은 4개 세션 단위 truncated BPTT를 사용하되 상태 값은 대화 끝까지 유지한다. LongMemEval QA 점수로 모델·epoch·하이퍼파라미터를 고르지 않는다.

## 평가와 판정

LongMemEval-S cleaned 전체 500문항을 사용한다. 저장소 revision은 `9e0b455f4ef0e2ab8f2e582289761153549043fc`이다. 데이터 revision, 파일 SHA-256, 코드 사본, 설정, 모델 해시는 별도 기록한다. 입력 데이터와 채점용 정답 파일은 물리적으로 분리하고 근거 주석은 입력 파일에서 제거한다. 공식 `get_anscheck_prompt`와 `yes` 판정 규칙을 그대로 사용한다.

질문 검색은 Mem0의 벡터 검색 top-20, 답변은 검색된 기억과 질문 시점만 사용한다. 타임스탬프를 모든 조건의 세션 입력에 동일하게 제공하고 실제 저장 시점과 대화 시점을 혼동하지 않는다. 대화별 저장소는 독립이다.

upstream 사실 추출 프롬프트는 import 시점의 실제 날짜를 삽입한다. 여러 날에 걸친 실행에서 조건별 입력과 캐시가 달라지지 않도록 이 문자열만 실험 시작일 2026-09-26으로 고정한다. 첫 실행 당시 기본 프롬프트와 같으며, 모든 대화의 실제 시점은 별도의 세션 날짜로 제공한다.

전체 정확도, question type별 정확도, abstention 부분집합 정확도를 보고한다. 지식 갱신·시간 추론이 핵심 분석이다. 단일 seed 점수와 문항 단위 paired bootstrap 95% 구간을 보고한다. seed 간 변동은 주장하지 않는다. LLM 기준군 대비 정확도 차이의 구간 하한이 -2 percentage points보다 높으면 사전 정의한 비열등 기준을 충족한다. 상황추적기 − 작은 모델 차이의 구간 하한이 0보다 높아야 상태 추적의 이득을 뒷받침한다. 이득이 없으면 그대로 부정적 결과로 보고한다.

비용은 추출·결정·문장 생성·답변 단계별 API 입력/출력 토큰을 분리한다. 가격 환산은 참고값이며 실제 proxy 청구 금액과 구분한다. 상황 상태 갱신의 인코딩·계산 시간과 학습 GPU 사용도 별도 보고한다. API 캐시를 쓰는 전체 실행 시간을 실제 비캐시 서비스 지연시간으로 주장하지 않는다. 일부 문항 또는 일부 seed만 끝난 상태에서는 전체 점수를 생성하지 않는다.

## 실행 및 복구

API 동시성은 `tune_workers.py`에서 새로 만든 가상 기억 예문으로 단계별 측정한다. 요청 재시도를 끄고 오류·처리량 포화·시험 상한 중 먼저 도달한 지점에서 멈춘다. `workers.json`의 오류 없는 후보 중 최고 처리량의 90% 이상을 내는 가장 작은 worker 수를 수집·평가에 적용한다. 이는 짧은 부하 시험 결과이며 장기 안정성을 보장하지 않는다. 합성 대화 생성은 긴 출력 때문에 최대 16 workers, 별도 모델인 공식 채점은 기존 동시성을 유지한다.

수집·평가는 한 프로세스 안에서 인코더와 API 연결 풀을 공유하고, 각 worker는 독립된 대화 상태·기억 저장소·비용 기록을 사용한다. 세션 순서는 유지하면서 서로 다른 대화를 병렬 처리한다. 활성 대화 수만큼만 데이터를 읽어 전체 벤치마크를 메모리에 올리지 않는다. API workers와 VESSL JOB 수는 별개다.

프로젝트의 `EACL/.env`를 API 자격증명의 우선 출처로 사용한다. 파일 값은 로그·업로드에 넣지 않는다. 학습 JOB에는 API 키가 필요하지 않다. 고정 encoder는 `all-mpnet-base-v2@e8c3b32edf5434bc2275fc9bab85f82640a19130`이다.

실험 출력은 `outputs/experiments/mem0_update_oss_s0/` 아래 둔다. 이전 GPT-4o-mini 사전검증 자료는 `mem0_update_v1/`에 따로 보존하며 학습 라벨·QA 결과를 섞지 않는다. `status.json`, `logs/`, `vessl_state.json`이 진행 상태를 담고, 최종 결과는 `results.json`과 `RESULTS.md`이다. `api.sqlite`와 `embeddings.sqlite`는 재시작 시 중복 API 호출·인코딩을 줄인다. 완료된 대화/문항은 설정 및 출처가 일치할 때 재사용한다.

VESSL은 GPU 1개짜리 JOB 두 개만 사용한다. 한 JOB은 작은 모델의 seed 0을 학습하고 다른 JOB은 상황추적기의 seed 0을 학습한다. 제출 전에 모든 활성·대기 JOB의 예약 GPU를 합산하여 동시 JOB ≤2, GPU 합계 ≤2를 검사한다. 실험 스케줄러는 파일 잠금과 고유 JOB 이름으로 중복 제출을 막는다. 다른 세션이 별도로 JOB을 제출하는 경우는 다음 조회 때 확인하며, 다른 사용자의 JOB을 임의 종료하지 않는다.

전체 실행 전 테스트, 실제 교사 기록 수집, 작은 데이터의 학습·복원, 공식 QA 입력·출력 경로를 확인한다. 검증된 파일을 `runtime/`에 고정한 뒤 driver를 실행한다. 실패한 GPU JOB을 무한 자동 재제출하지 않는다. 실패 이유와 로그를 확인한 후 같은 데이터 캐시와 기록을 유지해 수정한다.

사용자가 데이터 전송 승인 요청 이후 실험 진행을 승인했다. AkashML의 gpt-oss-120b로 공개 LongMemEval 및 합성 학습 대화를 처리하며 공식 채점기는 변경하지 않는다. 최초 4개 학습 대화의 생성·교사 기록 수집을 먼저 확인한 뒤 전체 파이프라인을 이어간다.
