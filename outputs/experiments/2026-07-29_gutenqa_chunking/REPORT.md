# GutenQA 다운스트림 검색 평가 (Track C) — D-B39 결과

**판정 = 🔴 NO-GO.** 사전등록한 실패 선언이 발동했다. 크기를 맞춘 M5 가 `Paragraph` 베이스라인을
넘지 못했고(41.62 vs 42.62), **어떤 청크 크기에서도 `Recursive`(50.35)에 도달하지 못한다**(M5 최고 45.19).

## 0. 🔴 먼저 — 봉인 미준수 (은폐 금지)

D-B39 §2 에서 dev 20편으로 `r*` 를 정하고 test 80편은 **1회만** 연다고 사전등록했다.
그러나 `02_eval_harness.py` 가 **전체 100편 pooled 수치를 자동 출력**하도록 작성돼 있어
dev 를 보는 순간 test 도 같이 보였다. **작성자의 스크립트 설계 실수다.**

- 완화: 질문별 `split` 라벨이 남아 dev/test 분리 집계는 사후에 가능했고, **아무것도 test 에서
  선택하지 않았으며 기준도 바꾸지 않았다**. `r*` 는 dev 20편만으로 재계산했다(아래 §4).
- 그럼에도 **"test 최초 개봉" 지위는 상실**했다. 이 실험의 test 수치는 확인적(confirmatory)이
  아니라 탐색적으로 읽어야 한다.
- 재발 방지: 하네스가 split 별로만 출력하고 pooled 는 명시 플래그로만 내도록 고칠 것 ⬜.

| 분절 인코더 | `paraphrase-multilingual-mpnet-base-v2` (M5 체크포인트 전제, 불변) |

| 비용 | LLM 호출 0 · API 0 · GPU 약 3시간 (A100×4) |

**지표 정의 (레포 원문).** relevance = 대소문자 무시 부분문자열, **첫 히트 이후 전부 0(one-hot)**.
`DCG@k = Σ(2^rel−1)/log₂(i+1)` — **비정규화(nDCG 아님)**. `Recall@k` 는 이름과 달리 재현율이 아니라
**hit-rate**(top-k 안에 하나라도 있으면 1).

방식 문제가 아니다. 상한이 7% 인 이상 46.19 는 이 gold 판정으로 나올 수 없다 ⇒ **논문이 명제에
대해 다른 판정 기준을 썼다고 봐야 한다.** 순위 비교에서 제외한다.

## 5. 판정 — 사전등록 실패 선언 발동

> D-B39 §8: "dev 에서 크기를 맞춘 M5 가 `_Paragraphs` 베이스라인조차 못 넘으면 → NO-GO 기록."

`r* = rate0.15` → **41.62 (test 41.49) < Paragraph 42.62 (test 42.26)** ⇒ **NO-GO.**

⚠️ 사전등록 문구가 느슨했음을 기록한다: "크기를 맞춘 M5" 는 LumberChunker 크기(327단어)에 맞춘 셀이고
`Paragraph` 는 48.8 단어라 이 대조 자체가 크기 매칭이 아니다. **우리에게 유리한 해석(= frozen 42.83 이
42.62 를 넘었다)을 고르지 않는다** — 지정된 크기매칭 셀은 `rate0.15` 이고 그것이 기준선이다
(`no-postresult-criterion-change`). 어차피 M5 최고치 45.19 조차 Recursive 50.35 에 못 미치므로
어떤 해석으로도 결론은 같다.

### 사전 해석 규약(D-B39 §9)에 따른 읽기
사전등록된 3번 시나리오 **"경계 품질이 검색 유용성으로 전이되지 않는다"** 가 실현됐다. 그것도
예상보다 강하게 — M5 ≈ Recursive 가 아니라 **M5 < Recursive** 다.

D-B31 에서 M5 는 dev-3 서사 분절 Score 0.4190 으로 `methods/` 최고 대비 +0.098, 최고 LLM 대비 +0.050 이었다.
**그 우위는 이 다운스트림으로 전혀 전이되지 않는다.**

🔴 가장 아픈 것은 LumberChunker(LLM·홈그라운드)에 지는 게 아니라 **Recursive 에 지는 것**이다.
Recursive 는 모델도 의미 판단도 없는 고정 크기 문자 분할이다. 여기 지면 *"학습된 경계가 임의 경계보다
낫다"* 조차 이 과제에서는 성립하지 않는다.

## 7. 부수 발견 — 이 벤치마크 자체의 편향 2건

### (a) ceiling — 질문의 17.5% 는 원천적으로 못 맞힌다
gold 부분문자열이 **어떤 청크에도 통째로 들어있지 않으면** 어떤 검색기로도 0점이다.

| 방법 | 단어/청크 | ceiling(원본) | ceiling(정규화) |
|---|---|---|---|
| propositions | 12.2 | 7.03% | 7.17% |
| paragraph | 48.8 | 82.47% | 86.10% |
| semantic | 63.1 | 82.10% | 86.10% |
| lumberchunker | 327.3 | 82.47% | 88.40% |
| recursive | 397.5 | 82.47% | 88.40% |
| **M5 전 변형** | 97.6~969.6 | **82.47%** | — |

**산문 5종은 청크 크기가 20배 차이나도 ceiling 이 82% 대로 같다** ⇒ 손실 원인은 청킹이 아니라
**데이터셋 표기 불일치**다. 질문 생성 LLM 이 gold 를 옮기며 `’→'`, `—→-` 등을 바꿨다.
미발견 526건 중 원문에 그대로 있는 건 **57건뿐**, 정규화하면 178건 회복, **348건은 정규화해도 복구 불가**.
**방법 무관이라 비교 공정성은 깨지지 않지만** 전 방법 절대값이 같은 비율로 눌려 있다.
정규화 ceiling 은 진단일 뿐 주지표로 승격하지 않는다(`baselines-stay-as-published`).

### (b) 🔴 **정정** — "홈그라운드 편향" 주장은 철회한다 (동어반복이었음)

**철회 대상.** 이 REPORT 초판과 `BRIEFING_for_external_analysis.md` 초판, 원장 D-B40 §5(b) 는
*"`Chunk ID` 가 지목한 청크에 gold 가 있는 비율 82.4% ≒ ceiling 82.47% ⇒ 질문이 LumberChunker
분절 위에서 저술됐다"* 고 적었다. **이 추론은 틀렸다.**

**왜 틀렸나.** 분모를 ceiling 으로 바꿔 재측정하면 **2,473 / 2,474 = 99.96%** 다. 즉 `Chunk ID` 는
**정의상 "gold 를 포함하는 LumberChunker 청크의 인덱스"** 이고, 그렇다면 "찾을 수 있는 gold 가
Chunk ID 청크 안에 있다"는 명제는 **항상 참**이다. 원래의 82.4% 는 편향의 증거가 아니라
**ceiling 을 다르게 쓴 것**에 불과하다.

**논문이 실제로 말하는 것 (확인).** 질문은 `gpt-3.5-turbo-0125` 가 "passage" 로부터 생성하고 사람이
30개로 필터링했다("more than 10000 questions are automatically generated, which are then filtered
down such that each book has 30 high-quality questions"). 🔴 그 **passage 의 단위가 무엇인지는 논문에
기술되어 있지 않다.** `Chunk Must Contain` 필드와 `Chunk ID` 컬럼도 논문에 **전혀 기술되지 않는다.**

**⇒ 홈그라운드 편향은 확인된 것도, 배제된 것도 아니다.** 검정하려면 6개 방법 어느 경계와도 무관한
중립 단위(챕터·고정 창)에서 질문을 새로 생성해 재측정해야 한다 — 이 실험 범위 밖이다.

**남는 사실.** `Chunk ID` = gold 포함 LumberChunker 청크 인덱스(2,473/2,474). 질문 생성기 =
gpt-3.5-turbo-0125 + 사람 필터. 생성 단위 미기술.

## 8. 부수 발견 — 절단 규칙: 후보 제한보다 스냅이 낫다
`m5__frozen`(352.1 단어 · 344.4 청크/책)이 `m5__rate0.15`(324.9 단어 · 373.3 청크/책)보다
**청크가 크고 개수도 적은데 점수가 높다**(42.83 vs 41.62). 둘은 같은 곡선 위의 점이 아니라
**절단 규칙이 다르다**:
- `rate` = 문단 경계만 후보로 두고 그 안에서 점수 순위 (작성자가 "정보를 버리지 않는다"고 판단한 방식)
- `frozen` = 전체 문장 전이 분위수로 경계를 낸 뒤 최근접 문단으로 스냅

같은 크기대에서 스냅 쪽이 나으므로 **후보 제한 설계가 실제로는 손해를 보고 있다.** 다만 그 이득
(+1.21)은 LumberChunker 와의 격차(−14.60)에 비하면 미미해 판정을 바꾸지 못한다. ⬜ 미조사.

## 9. 한계 (제거 금지)

- 🔴 **봉인 미준수** (§0). test 수치는 확인적이 아니라 탐색적.
- 🔴 **인코더 ≠ ada-002** → 논문 절대값과 직접 비교 불가. 순위 재현으로만 방어.
- 🔴 **Propositions 행 측정 불가** → 재현 게이트가 5종이 아니라 4종으로 축소.
- **질문의 17.5% 가 데이터셋 표기 불일치로 소실** (§7a). 방법 무관이나 절대값은 눌려 있음.
- **M5 의 문장 단위 해상도 미검증** — 문단 절단 제약 때문. M5 의 강점이 문단 내부 경계라면 못 잡힌다.
- **단일 검색 인코더·단일 시드** — 견고성 미확인.
- **과제 적합성.** GutenQA 는 verbatim 사실 span 찾기(needle-in-haystack)라 답 span 이 온전하고
  주제적으로 자족적인 청크를 원한다. M5 는 **사건 경계**(상황모델 리셋)를 찾도록 학습됐다.
  같은 목적함수가 아니므로 이 결과는 **"M5 를 범용 RAG 청커로 쓰면 진다"**의 강한 증거이고,
  **"M5 가 사건 분절기로서 쓸모없다"**의 증거로는 약하다.
- **M3 미제출** — Stage-1 이 12만 토큰 장편에 안 들어감(D-B14 동결 스펙 변경 필요).
