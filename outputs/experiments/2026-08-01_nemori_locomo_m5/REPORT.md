# LoCoMo × Nemori — 분절기를 M5 로 교체한 결과 (2026-08-01 KST)

> 사전등록 `PRE_REGISTRATION.md` · 재현 방법 `README.md` · 표 원본 `RESULTS_TABLES.md`
> 방법론 `context/methodology/nemori-m5-locomo.md` · 원장 D-L01 / D-L02

## 0. 결론 먼저

1. **하네스는 발표판을 재현한다.** baseline 팔 LLM judge **0.8351** vs 논문 README **0.8305**
   (카테고리별 문항 수까지 일치). 비교 기준선으로 쓸 수 있다.
2. **M5 로 교체하면 진다 — 그리고 과분절을 고쳐도 진다.**
   | 팔 | 분절 그룹 수 | LLM judge | Δ vs baseline | 95% CI |
   |---|---|---|---|---|
   | baseline (발표판 LLM 분절) | 503 | **0.8351** | — | — |
   | m5 (c=1.0, 동결값) | 958 (1.90×) | 0.8097 | −0.0255 | [−0.0445, −0.0059] |
   | m5 (c=1.5, **개수 정합**) | 494 (0.98×) | 0.8026 | **−0.0334** | [−0.0530, −0.0131] |
   둘 다 CI 가 0 을 포함하지 않는다.
3. **"과분절만 고치면 된다"는 가설은 기각됐다.** c 를 올려 그룹 수를 발표판과 같게(494 vs 503)
   맞췄더니 **더 떨어졌다.** 즉 문제는 경계 *개수* 가 아니라 **경계 *위치*** 다.
4. **역설: 증거 턴은 더 잘 찾는데 답은 더 틀린다.** m5(c=1.5)의 증거 턴 재현율은 **0.8995** 로
   발표판 0.8716 을 **앞선다**(full_hit 0.8633 vs 0.8320). 그런데 질문당 회수 턴이
   176 → **298 개**, 컨텍스트가 4,110 → **5,615 토큰**으로 불어났다.
   ⇒ 재현율 상승은 **더 잘 겨냥해서가 아니라 검색 단위가 커져서**다. 희석(dilution)이다.
5. 사전등록 §6 판정 규칙에 따라: **"LoCoMo 다운스트림에서 M5 분절기는 Nemori 의 LLM 분절기보다
   나쁘다. 임계 c 로는 회복되지 않는다."** 로 기록한다.

🔴 **봉인 상태 고지**: c=1.0 팔만 "봉인된 test 1회 개봉"이다. **c=1.5 는 c=1.0 결과를 본 뒤 고른
값**이므로, 이 시점부터 LoCoMo 는 held-out test 가 아니라 **dev** 다. c=1.5 수치를 일반화 근거로
인용할 수 없다. 이후 주장하려면 새 held-out 이 필요하다.

## 1. 실험 setup

### 1.1 목적
Nemori(`nemori-ai/nemori`, arXiv 2508.03341)의 **에피소드 경계 결정 모듈만** 우리 M5 로 바꿨을 때
LoCoMo 다운스트림(사건 단위 retrieve → QA)이 어떻게 되는지. 우리 기여 주장은 "사건 단위 분절"
하나이며 retrieval·QA·메모리 구조는 Nemori 것을 그대로 쓴다.

### 1.2 데이터
`benchmarks/locomo/locomo10.json` — 10 대화 · **5,882 메시지** · QA 1,986문항.
채점은 발표판 `evals.py` 규칙대로 카테고리 5(446문항, adversarial) 제외 → **1,540문항**.

### 1.3 팔 — 차이는 분절기 **하나뿐**

| 팔 | 분절기 | 조건 |
|---|---|---|
| `baseline` | `nemori.llm.generators.segmenter.BatchSegmenter` (원본) | gpt-4.1-mini, temp 0.2, JSON 모드, 80메시지 청크 |
| `m5` | `hi_ontop.nemori_segmenter.M5BatchSegmenter` | 적응임계 **c=1.0** (동결값, 사전등록) |
| `m5_c1p5` | 〃 | 적응임계 **c=1.5** (🔴 결과를 본 뒤 선택 — §0 고지) |

원본 저장소 파일 **무수정**. `nemori.core.memory_system.BatchSegmenter` 모듈 전역 이름만 치환하고,
`add.py`/`search.py`/`evals.py`/`generate_scores.py` 는 `runpy` 로 **원본 그대로** 실행.
팔마다 `agent_id`·Qdrant 컬렉션 접두사를 분리(`locomo_baseline` / `locomo_m5` / `locomo_m5_c1p5`).

### 1.4 HP (발표 설정 그대로, 손대지 않음)
`llm_model` gpt-4.1-mini · `embedding_model` gemini-embedding-001 (3072d) ·
`buffer_size_max 20` · `episode_min_messages 1` · `batch_threshold 20` ·
`enable_semantic_memory true` · `enable_prediction_correction true` ·
`enable_episode_merging true` (threshold 0.85, top-k 5) ·
`search_top_k_episodes 10` · `search_top_k_semantic 20` ·
검색 `--search-method vector` · `--include-original-messages-top-k 2` · 심판 gpt-4.1-mini temp 0.

**M5 쪽**: 체크포인트 `models/m5_default/M5.pt`(I2, 2026-07-31 동결 디폴트) ·
신호 `s = Σ_k P(reset_k)` 5축 · `online_nf` · 단위 = 메시지(turn) · 화자 접두사 없음 ·
청킹 없음 · device CPU. c 외 모든 값이 두 M5 팔에서 동일하다. seed 개념 없음(결정적).

### 1.5 지표
주지표 = **LLM judge 정확도**(발표판 headline). 보조 = BLEU-1 · token F1.
추가로 **증거 턴 재현율**(LLM 무관, `evidence_recall.py`) 과 비용 지표.

## 3. 해석

### 3.1 과분절 가설은 기각됐다
c=1.0 결과만 봤을 때의 유력한 설명은 "M5 가 1.9배 과분절해서 진다"였다(D-B34/B37/B38 의 서사
과분절과 같은 원인). c 를 1.5 로 올려 **분절 밀도를 발표판과 정합**시킨 결과(494 vs 503),
정확도는 회복되기는커녕 **−0.0255 → −0.0334 로 더 떨어졌다.**
⇒ **개수는 병목이 아니었다. 병목은 경계가 *어디에* 놓이느냐다.**

### 3.2 재현율↑ · 정확도↓ 를 어떻게 읽나 — 희석
c=1.5 는 증거 턴 재현율에서 **발표판을 이긴다**(0.8995 vs 0.8716). 이것만 보면 "검색은 더 잘한다"
로 읽고 싶어진다. 그런데 같은 top-10 에피소드가 담아 오는 원본 턴이 **176 → 298 개**로 늘었다.
큰 에피소드를 뽑으면 증거가 그 안에 들어 있을 확률은 자동으로 올라간다 — **정밀도를 버리고 산 재현율**이다.
그 대가가 QA 프롬프트 **+37% 토큰**이고, 관련 없는 대화가 섞이면서 답이 더 틀렸다.

즉 **증거 턴 재현율은 단독으로 읽으면 안 된다** — 회수 턴 수와 짝지어야 의미가 있다. 이번 실험에서
얻은 방법론적 교훈이다.

### 3.3 왜 경계 위치가 나쁜가 (가설, 미검정)
- **도메인**: M5 는 영어 서사 픽션 앵커로 학습됐다(D-M8). 5축(주인공/공간/시간/인과/의도) 리셋은
  서술문에서 정의된 것이고, 대화의 화자 교대·인접쌍·주제 재개는 그 축에 잘 안 실린다.
- **Temporal 이 가장 크게 진다**(−0.066). LoCoMo 의 시간 정보는 **세션 단위**로 붙는데
  (세션 하나 = 타임스탬프 하나), M5 는 세션 경계를 특별 취급하지 않는다. 반면 LLM 분절기는
  프롬프트에 "30분 이상 시간 간격"을 명시적으로 넣어 세션 경계를 잡는다.
  **이건 M5 가 못 쓰는 신호를 baseline 이 쓰는 것**이므로 공정성 문제가 아니라 방법 차이다.
- **에피소드 크기 폭주**: c=1.5 에서 최대 에피소드가 **252 메시지**다(baseline 67). 적응임계
  `μ+cσ` 는 신호가 평탄한 구간에서 경계를 아예 안 내므로 긴 저-신호 구간이 통째로 한 덩어리가 된다.
  대화에서 그 구간이 세션 여러 개를 삼킬 수 있다.

### 3.4 유일하게 이긴 축
분절 단계 LLM 을 **완전히 없앴다**(79콜 · 37.3만 토큰). c=1.5 에서는 하류 비용 증가가 없어
**주입 총비용이 발표판과 동률**이다. 분절은 CPU 439초로 끝나고 GPU 가 필요 없다.
다만 그 절감(주입 토큰의 11%)이 **정확도 −0.033 의 대가로는 비싸다.**

## 5. 한계 / 검증 미해결 (제거 금지)

1. 🔴 **c=1.5 는 LoCoMo 결과를 보고 고른 값이다.** 이 시점부터 LoCoMo 는 held-out test 가 아니라
   **dev** 다. c=1.5 수치를 일반화 근거로 인용할 수 없다. c=1.0 팔만 봉인 상태 1회 개봉이다.
   (다만 이번엔 선택이 **우리에게 불리한 방향**으로 나왔으므로 "dev 에서 유리하게 골랐다"는
   비판은 이 결과엔 해당하지 않는다.)
2. 🔴 **run 1회, seed 없음.** 부트스트랩은 **문항 표본오차만** 반영한다. 파이프라인 확률성
   (분절 LLM temp 0.2, 에피소드/시맨틱 생성 기본 temp 0.7, 병합 판정)은 CI 에 안 들어가 있다.
   실제 불확실성은 보고된 CI 보다 크다.
3. 🔴 **topic 문자열 비대칭 — 통제 안 됨.** baseline 은 LLM 이 만든 topic 이 에피소드 생성 프롬프트의
   `Boundary detection reason` 자리에 들어가고, M5 팔은 `"conversation"` 만 들어간다.
   방향은 우리에게 불리하지만 크기를 모른다. → baseline 을 `topic="conversation"` 으로
   한 번 더 돌리면 분리된다(미실행).
4. 🔴 **M5 는 영어 서사 픽션 앵커 학습**(D-M8). 이번 결과는 "M5 라는 방법이 나쁘다"가 아니라
   "**이 체크포인트를 이 도메인에 그대로 쓰면 진다**"까지만 말한다.
5. **주입 프로토콜을 `single-flush` 로 고정**했다(사전등록 E5). 세 팔에 동일 적용했고 baseline 이
   발표 수치를 재현했으므로 큰 왜곡은 없어 보이나, **발표 기본값 재현 팔은 돌리지 않았다.**
6. **upstream 버그 2건을 고친 상태의 수치다**(사전등록 부칙 1: 턴 순서 tiebreaker 누락 · JSONB
   문자열 반환). 세 팔 동일 적용이며 고치는 방향이 baseline 을 강하게 만든다.
   원본 저장소를 그대로 돌리면 이 표와 다른 수치가 나온다.
7. **증거 턴 재현율은 텍스트 매칭 기반**이다(메시지 metadata 에 `dia_id` 가 보존되지 않아 본문으로
   역매핑). 누락은 없었지만(`episodes_not_found: 0`), 동일 문장이 두 번 나오면 앞쪽 턴으로 붙는다.
8. 카테고리 3(Open-Domain)은 n=96 으로 작다. 카테고리별 Δ 에는 개별 CI 를 붙이지 않았다 —
   **카테고리 표는 방향 확인용**이고 판정은 전체 Δ 로 한다.
9. §3.3 의 세 가설(도메인·세션경계·크기폭주)은 **이번 실험으로 검정하지 않았다.**
10. LLM judge 자체가 gpt-4.1-mini 다. 세 팔에 같은 심판이지만 심판 편향은 공통으로 남는다.
