## 0. 왜 다시 여나 — D-B30 기각을 뒤집을 근거 2개

D-B29/D-B30 에서 Ψ 묶음(4 run)은 **최고 Δ −0.0006**(기준선 0.4056)으로 사전 기준 +0.005 에
미달해 기각됐다. 그럼에도 재개봉하는 근거는 둘이고, 둘 다 사실 확인됨:

1. **ψ 가 반쪽만 켜진 조건에서 시험됐다.** Ψ 묶음은 `head_feat=delta` 로 돌았고, 그 조건에서
   `change_probs_rollout`/`forward_batched` 는 `sh`(=`f(s;ψ)` 예측)를 **head 입력에 넣지 않는다**
   (`src/hi_ontop/factored_slot.py:471` — `if self.head_feat != "delta"` 안에서만 `sh` 계산).
   즉 §4.3 이 주장한 *"ψ 조건부 dynamics 의 예측 실패 = 경계"* 경로는 판정기에 연결되지 않은 채
   시험됐다. ψ 는 head 에 붙은 추가 특징일 뿐이었다.
2. **앵커 라벨이 그때와 다르다.** Ψ 묶음의 split 은 구 `phase1`. 현재는 의도축 교체(`phase1_i2`)와
   인과축 Qwen3.6 사슬 교체(`phase1_chainq_i2`)가 적용된 다른 라벨이다. D-B30 이 지목한 남은
   병목이 *앵커 라벨 노이즈* 였으므로, 라벨이 바뀐 지금 재측정은 그 결론 자체에 대한 검정이다.

⚠️ `phase0-decisions-and-runs.md:5946` 의 "새 ψₑ 변형 추가 금지(codex 고정 조건)" 를 **사용자 지시로
해제**하고 착수한다. 단 **새 변형은 만들지 않는다** — 기존 `cummean`/`ema` 구현 그대로다.

## 1. 이번 배치의 지위 — **선별(screening)이지 채택 결정이 아니다**

사용자 지시: seed 1개로 빨리 본다. D-B30 에서 측정된 **같은 설정 seed 간 std = 0.00078** 이므로
1-seed 차이는 ±0.002 규모까지 무의미하다. 따라서 **이 배치 결과만으로 ψ 채택을 결정하지 않는다.**
이 배치가 정하는 것은 오직 **"3-seed 본선을 돌릴 값어치가 있는가"** 하나다.

## 2. run 매트릭스 (8 run · seed 0 · dev-3 미개봉)

(= 두 split 기준선과 동일 설정) · `--dev3` **안 켠다** · epochs 8 · slot_dim 128 · bn 8 · lr 3e-4

|---|---|---|---|
| **A** | cummean | delta | D-B29 Ψ 재현 — 새 앵커에서도 같은가 |
| **B** | ema | delta | 〃 |

| **D** | none | resid_signed | **대조군** — C 의 이득이 ψ 덕인지 resid_signed 덕인지 분리 |

## 3. 🔒 게이트 (사전 확정 — 결과 보고 안 바꾼다)

지표는 **J_anchor** (앵커 val 5-fold OOF deployable Score) 하나만 본다. AUC 는 보조.

- **G1 — ψ 자체**: A 또는 B 가 같은 split 의 seed0 기준선 대비 **+0.005 이상**
- **G2 — ψ 조건부 dynamics**: **C − D ≥ +0.005** (같은 split, 같은 seed).
  C 가 기준선보다 높아도 D 도 같이 높으면 그건 **resid_signed 의 공이지 ψ 의 공이 아니다.**
- **본선 진출 조건**: G1 또는 G2 를 **두 split 중 최소 1곳에서** 통과. 통과한 조건만 3-seed 로 확장.
- **전부 미달이면**: D-B30 과 같은 형식으로 기각 기록하고 종료. ψ 트랙을 닫는다.
- dev-3 는 이 배치에서 **열지 않는다**. 본선(3-seed)까지 통과한 단일 조건에 대해서만 개봉한다.

## 4. 자원 결정 — VESSL Job 안 씀 (로컬 A100 4장만)

사용자는 "Job 4개 + 로컬 GPU 4개"를 지시했으나 **로컬만 쓴다**. 근거:
- run 1개 = GPU util ~22% · VRAM 3.5GB (`db29_launch.sh` 주석의 실측). 80GB A100 4장에 8 run 을
  동시에 올려도 남는다 → 8 run 이 **1 웨이브**로 끝난다.
- VESSL 경로는 `/shared` 스테이징 + 큐 대기가 붙고 `resourcespec-a100x1` 이 **$1.55/hr/job**.
  벽시계가 줄지 않는데 비용만 든다.
⇒ "최대한 빨리" 에 대한 답이 로컬이다. 매트릭스를 3-seed(24 run)로 늘려도 로컬 1~2 웨이브다.

## 7. 🔴 전처리 점검 중 발견 — val 세트의 책 단위 누수 (결과 나오기 전 기록)

배치 실행 중 코퍼스 전처리를 점검하다 발견. **이번 배치가 만든 문제가 아니라 D-B29 라인 전체가
깔고 있던 조건**이므로 여기 기록하고 후속 검정을 건다.

**정상 확인된 것**: emb↔index 정합(2,788,159 문장 = `sent_offsets[-1]`) · 전이수 = 문장수−문서수
(**문서 경계를 넘는 전이 없음**) · resets {0,1} · 임베딩 L2=1.0 정규화, NaN/0벡터 없음 ·
인코더 `paraphrase-multilingual-mpnet-base-v2` fp16 · **dev-3(pieman/tunnel/monkey) ∩ 학습 코퍼스 = ∅** ·
doc_id 중복 0 · i2 vs chainq 는 **인과축만** 다름(나머지 4축 100% 동일).

**문제**: 학습 코퍼스는 구텐베르크 3,032권을 10,598 청크로 자른 것인데(`pg112_000`, `pg112_001`, …),
train/val 분할이 **청크 단위 무작위**다 (`train_anchor_m4m5.py:419`, 분할 seed 20260728 고정).

```
train 10,069 청크 / val 529 청크
val 청크의 80.2% 는 같은 책의 다른 청크가 train 에 있다 (겹치는 책 329권)
```

⇒ **J_anchor 절대값은 일반화 성능보다 낙관적**이다. 같은 책의 다른 부분을 이미 학습한 상태에서
채점한다(같은 등장인물·배경·문체·같은 라벨러 습관).

**이번 배치 판정에 대한 영향 — 사용자 판단(2026-08-01): 배치는 그대로 완주한다.**
- 8 run 과 기준선이 **전부 동일 분할·동일 val** 을 쓰므로 **조건 간 비교(=§3 게이트)는 유효**하다.
- 영향받는 것은 절대 숫자이지 ψ 유무의 상대 비교가 아니다.

## 8. 후속 — 책 단위 분할 재확인 (사전 확정, 결과 보기 전)

본 배치 종료 **후** 실행한다. 목적은 두 가지이며 둘 다 사전에 고정한다.

1. **누수 크기 측정**: 같은 설정(psi none · delta · seed 0)을 **책 단위 분할**(같은 책은 train/val
   한쪽에만)로 재학습해 J_anchor 낙폭을 잰다. 이 값 없이는 0.4179 를 논문에 못 쓴다.
2. **깨끗한 분할에서의 ψ 재판정**: §2 의 4 조건(A/B/C/D)도 책 단위 분할로 같이 돌린다.
   누수가 ψ 판정을 가리고 있었을 가능성을 배제하기 위함이다.

- 매트릭스: 2 split × {기준선(none·delta), A, B, C, D} × seed 0 = **10 run**, 로컬 1 웨이브.
- 🔒 **게이트는 §3 과 동일**(+0.005 · C−D). **책 분할 결과를 보고 청크 분할 결과를 사후 채택하거나
  그 반대를 하지 않는다.** 두 분할은 각각 독립적으로 판정하고, **불일치하면 책 단위 분할을 신뢰**한다
  (누수 없는 쪽이 옳다). 이 우선순위를 결과 보기 전에 확정한다.
- 구현: `train_anchor_m4m5.py` 에 `--group-split book` 플래그 추가(기본 off = 현행 동작 그대로,
  기존 산출 재현성 불변). **본 배치가 끝난 뒤에 수정한다** — 실행 중 스크립트 수정 금지.
- 산출 네임스페이스: `--ns-suffix booksplit`.
